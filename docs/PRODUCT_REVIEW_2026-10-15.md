# Product review: แผนใช้เงินรายวันและการค้นพบฟังก์ชัน

วันที่ตรวจ: 15–16 ตุลาคม 2026 (เวลาไทย)

นี่คือการตรวจจากโค้ด การทดลองใช้งาน และการจำลองมุมมองผู้ใช้/กรรมการ/ผู้บริหารโดยผู้พัฒนา ไม่ใช่ผลสัมภาษณ์หรือ usability study กับผู้ใช้จริง และไม่ใช่การรับรองระบบธนาคาร

## ฟังก์ชันมีอยู่จริงหรือไม่

มีอยู่จริงทั้งในโปรเจกต์เดิมและเว็บนี้ แต่ต้องแยกสามสิ่งออกจากกัน:

1. **รายจ่ายที่คาดว่าจะเกิด:** โมเดล ONNX/LightGBM ใน `src/app_v2.py` สร้าง `predicted_spend` ของแต่ละวันในอนาคต กราฟใช้ตัวเลขเหล่านี้รวมบิลและเงินเดือนเพื่อคาดการณ์ยอดคงเหลือ ข้อมูลทั้งหมดเป็นข้อมูลสมมติ
2. **งบที่ควรใช้ต่อวัน:** `src/flowsense_engine.py` คำนวณจากยอดบัญชี บิลที่ต้องจ่ายก่อนเงินเดือน เงินสำรอง และวันคงเหลือ เป็นสูตรจัดสรรเงินที่อธิบายได้ ไม่ใช่ผลทำนายโดยตรงจากโมเดล
3. **วันนี้ใช้เพิ่มได้อีก:** งบทั้งวันลบรายจ่ายที่บันทึกแล้ว โดยไม่ใช้เงินที่กันไว้สำหรับบิลและเงินสำรอง

ก่อนแก้ UI คำแนะนำงบรายวันอยู่ใต้กราฟขนาดใหญ่ วัดจากหน้าแรกขนาด 1280×720 พบตำแหน่งกล่องงบประมาณ 1,831 px จากด้านบน ผู้ใช้ต้องเลื่อนหลายช่วงจอ และทางเข้าหลักใช้คำว่าออมเงิน/บัญชี จึงไม่สื่อว่ามีเครื่องมือวางแผนรายวัน

## สูตรและขอบเขตของเครื่องมือใหม่

```
งบทั้งวัน = max(0, (ยอดบัญชีปัจจุบัน + ใช้ไปแล้ววันนี้ − บิลก่อนเงินเดือน − เงินสำรอง) / วันจนถึงเงินเดือน)
ใช้เพิ่มวันนี้ = max(0, min(เงินที่ยังไม่ถูกกันไว้, งบทั้งวัน − ใช้ไปแล้ววันนี้))
```

วันจนถึงเงินเดือนนับรวมวันนี้และสิ้นสุดวันก่อนเงินเดือนเข้า งบปัดลงเป็นสตางค์ ยอดใช้แล้วกับยอดแสดงผลใช้หน่วยสตางค์เดียวกัน เช่น ยอดก่อนใช้ 5,000 บาท บิลและเงินสำรองรวม 2,000 บาท เหลือ 3 วัน จะมีงบ 1,000 บาท/วัน เมื่อใช้ 200 บาทและบัญชีเหลือ 4,800 บาท งบทั้งวันยังเป็น 1,000 บาท และใช้เพิ่มได้ 800 บาท

เครื่องมือลองตั้งงบสมมติว่าใช้ตามงบเดียวกันทุกวัน จ่ายบิลตามรายการที่ทราบ และไม่ดึงเงินออมหรือนับเงินเดือนก่อนวันเข้า รายจ่ายที่จ่ายแล้วไม่ถูกย้อนคืนเมื่อปรับงบต่ำลง ผลจำลองตามงบจึงเป็นคนละชุดกับกราฟคาดการณ์จากโมเดล การโอนออกในต้นแบบนับเป็นการใช้จ่ายวันนี้; ยังไม่มีระบบจำแนกหมวดธุรกรรมจริง

## การตรวจความปลอดภัย

- ตรวจโค้ด session, CSRF/origin, input validation, idempotency, token และส่วนติดต่อผู้ใช้ที่ทำรายการ
- ชุดทดสอบครอบคลุมการแยกยอด/ประวัติแต่ละผู้เยี่ยมชม การหักเงินซ้ำพร้อมกัน origin/CSRF, cookie flags, request limits, session หมดอายุ, token ที่ถูกแก้ไข/ใช้ซ้ำ/ใช้ข้าม session และการระงับบัญชีจำลอง
- `npm audit` และ `pip-audit` ของ dependency lock ไม่พบช่องโหว่ที่มีรายงาน ณ เวลาตรวจ
- UI ไม่ขอข้อมูลบัญชีจริงหรือเปิดกล้อง การยืนยันตัวตน 5 วินาทีเป็น simulation ปุ่มยกเลิกยังทำงานโดยไม่หักเงิน
- การโหลดข้อมูลหลังเปลี่ยนโปรไฟล์จะไม่เขียนผลของโปรไฟล์เดิมทับโปรไฟล์ที่เลือกใหม่

ผลเหล่านี้เป็นขอบเขตที่ตรวจได้ในต้นแบบ ไม่ครอบคลุมการเจาะระบบโดยอิสระ การประเมินโมเดลกับข้อมูลจริง การกำกับดูแลทางการเงิน หรือความพร้อมทำธุรกรรมธนาคาร ระบบยังเก็บสถานะในหน่วยความจำหนึ่ง process และ session หมดอายุหนึ่งชั่วโมงหลังสร้าง

## สิ่งที่ควรวัดกับผู้ใช้จริงในรอบถัดไป

ให้ผู้ใช้ใหม่ห้าคนลองตอบ “วันนี้ใช้เพิ่มได้อีกเท่าไร” และ “ถ้าใช้วันละ 1,000 บาทจะเกิดอะไรขึ้น” โดยไม่อธิบายหน้าจอล่วงหน้า บันทึกความสำเร็จ เวลาในการหา คำที่เข้าใจผิด และความมั่นใจในการตัดสินใจ การเปลี่ยนครั้งนี้ยังไม่ใช่หลักฐานว่า retention, conversion, เงินออม หรือความเสียหายจากการหลอกลวงดีขึ้นจริง
